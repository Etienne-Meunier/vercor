# VerCOR 0.4.3 Release Design

## Context

The immutable `v0.4.2` tag points to commit
`180c08646e72b85186810142010ae699396976fc`. Its tag-triggered workflow passed
the build, installed-artifact, external-extension, macOS, quality, and release
preflight gates, then PyPI rejected both distributions because
`License :: OSI Approved :: Apache-2.0` is not a valid Trove classifier. PyPI
0.4.2 and the GitHub Release were never created.

Current `main` is 11 commits ahead of `v0.4.2`. Those commits replace the
invalid classifier with `License :: OSI Approved :: Apache Software License`,
reject duplicate license classifiers, and make `pyproject.toml` the sole
executable VerCOR version owner for the GitHub workflow and distribution
checks. The latest `main` workflow run succeeded. The `v0.4.3` tag, PyPI
version, and GitHub Release are absent.

## Goal

Prepare, review, merge, tag, publish, and verify VerCOR 0.4.3 through the
documented release path without modifying any historical tag or using a manual
publication path.

## Release Scope

The 0.4.3 release commit will make only the active release changes needed on
top of current `main`:

- Set `project.version` in `pyproject.toml` to `0.4.3`.
- Update executable release-policy expectations that describe the active
  changelog entry and 0.4.3 recovery record.
- Update README installation and current-release guidance to 0.4.3.
- Add a dated 0.4.3 changelog entry and comparison link.
- Add `docs/release-notes-0.4.3.md`.
- Move the active candidate, artifact, branch, tag, PyPI, GitHub Release, and
  recovery commands in `docs/releasing.md` from 0.4.2 to 0.4.3.
- Record final local and hosted release evidence in `PROGRESS.md`.

The release notes and changelog will state that:

- `v0.4.2` remains immutable;
- its publication failed because of the invalid license classifier;
- no 0.4.2 PyPI version or GitHub Release was created;
- 0.4.3 carries the canonical Apache classifier and duplicate-classifier
  regression protection; and
- release artifact identity now derives from the version in
  `pyproject.toml`.

The existing post-0.4.2 changes in `.github/workflows/python-package.yml` are
part of the 0.4.3 release. The release commit will not reintroduce a hard-coded
0.4.3 workflow version: the workflow must continue deriving its version, wheel
name, source-distribution name, tag guard, release notes path, PyPI URL, and
GitHub Release identity from `pyproject.toml`.

Historical evidence and historical version references remain unchanged where
they describe earlier tags, commits, release attempts, migration contracts, or
third-party compatibility floors such as `vercor>=0.4.0,<0.5`.

## Validation Design

Implementation follows a release-specific red/green cycle:

1. Update the supervised active-release expectations to 0.4.3 and confirm they
   fail against the 0.4.2 candidate.
2. Update package metadata and release documentation, then rerun the focused
   release and distribution contracts.
3. Parse the workflow YAML and validate every embedded Bash block with
   `bash -n`.
4. Run Black, strict flake8, mypy, compileall, `git diff --check`, fast pytest,
   full pytest, and branch coverage at the configured 90% threshold.
5. Build exactly `vercor-0.4.3-py3-none-any.whl` and
   `vercor-0.4.3.tar.gz` in a fresh temporary directory.
6. Run Twine metadata checks, inspect wheel and source-distribution metadata,
   verify `vercor/py.typed`, and perform an outside-checkout installed-version
   smoke test.
7. Record exact test counts, warnings, artifact sizes, and SHA-256 values in
   `PROGRESS.md`, then rerun the release-focused gates and clean-tree checks.

No release commit may be merged while a required local or hosted check is
failing.

## GitHub and Publication Flow

All work occurs on the isolated `release/vercor-0.4.3` branch. The approved
design specification and implementation plan are committed before the release
candidate commit, as required by the repository's development workflow.

After local verification:

1. Push the exact release branch commit and open a draft pull request against
   `main`.
2. Require the exact pull-request workflow run to succeed.
3. Mark the pull request ready, merge it into `main`, fetch the protected
   branch, and bind `RELEASE_COMMIT` to the exact remote-main commit.
4. Recheck that local and remote `v0.4.3`, PyPI 0.4.3, and every GitHub Release
   state for `v0.4.3` are absent.
5. Create an annotated `v0.4.3` tag at `RELEASE_COMMIT`, verify that it peels to
   the exact remote-main commit, and push only that tag.
6. Monitor the exact tag-triggered workflow through completion.
7. Verify the published PyPI filenames and checksums, an isolated
   `vercor==0.4.3` installation, the published GitHub Release title and notes,
   and both hosted release assets.
8. Add and push a final documentation-only progress record only if doing so
   cannot alter the immutable release commit or tag.

The workflow is the only authorized publisher. If the tag-triggered workflow
fails, the tag remains immutable. Do not delete, overwrite, repoint, blindly
rerun, manually upload distributions, or mutate a partial hosted release.
Instead, inspect the exact public state and obtain explicit approval before
using any recovery procedure.

## Failure Handling

- If the release branch diverges from the intended `main`, stop before opening
  or merging the pull request.
- If `v0.4.3` or PyPI 0.4.3 appears during a later preflight, stop before
  creating or pushing the tag.
- If pull-request CI fails, diagnose the first failing boundary, add a
  regression test where applicable, and update the same release branch.
- If the tag workflow fails before publication, preserve the tag and report the
  exact failing job and hosted state.
- If publication becomes partial, use the documented exact-state classifier
  before proposing any recovery action.

## Success Criteria

The release is complete only when:

- `main` contains the reviewed 0.4.3 release commit;
- annotated tag `v0.4.3` peels to that exact commit locally and remotely;
- the exact tag-triggered GitHub Actions run succeeds;
- PyPI serves both 0.4.3 distributions with the CI-recorded SHA-256 values;
- a clean isolated environment imports installed VerCOR 0.4.3;
- GitHub publishes `VerCOR 0.4.3` with the committed notes and both matching
  assets; and
- `v0.4.0`, `v0.4.1`, and `v0.4.2` remain unchanged.
